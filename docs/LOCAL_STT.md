# Локальный транскрипт из WAV

## Автоматическая обработка записей

При работающем [локальном Mac](NGROK.md) включите обработчик один раз:

```bash
bash scripts/local-mac.sh auto-transcribe-on
```

Новые записи в `services/storage/listen-captures/` внутри локального state
автоматически обрабатываются после появления готового WAV и итоговой metadata.
Для завершения записи полностью закройте Omi на iPhone. После обработки откройте
приложение и обновите список разговоров: результат — «Локальная запись».

Каталоги записей, существовавшие при первом включении (включая незавершённые),
пропускаются. Их можно обработать вручную. Произвольные WAV за пределами capture
каталога также передаются ручной командой ниже.

```bash
bash scripts/local-mac.sh transcription-status
bash scripts/local-mac.sh auto-transcribe-off
```

В статусе видны работающий обработчик и количества ожидающих, обрабатываемых,
готовых и неудачных задач. `off` останавливает только обработку; WAV и результаты
сохраняются. Включённый обработчик запускается вместе со штатным `local-mac.sh up`
и останавливается при `down`. После перезапуска Mac сначала запустите этот стек.
Mac должен работать и не спать; новые записи, завершённые во время остановки
обработчика после первого включения, будут подобраны при следующем запуске.

## Обработка отдельного WAV

При работающем [локальном Mac](NGROK.md) выполните из корня репозитория:

```bash
bash scripts/local-mac.sh transcribe /path/to/audio.wav
```

Команда принимает законченный WAV PCM16 mono 16 kHz, запускает установленный
движок из настроек и сохраняет разговор для владельца подключения «Локальный Mac».
Обновите список разговоров в приложении, откройте «Локальная запись» и вкладку
транскрипта. Для capture используется дата из соседнего `metadata.json`;
для отдельного WAV — дата изменения файла.

Путь результата: WAV → локальный ASR + диаризация → JSON → локальный Conversation.
Приложение получает его через `GET /v1/conversations` и
`GET /v1/conversations/{conversation_id}` с прежним ключом подключения.
При открытии локального разговора LLM и облачные обработчики не запускаются.
Новых публичных write/STT-эндпоинтов нет.

## Выбор модели

Настройки читаются для каждой новой задачи из
`.local/dev-harness/ngrok/stt-engine.json` (при собственном state root — из
каталога соответствующего экземпляра). Файл необязателен; значения по умолчанию:

```json
{
  "engine": "whisperx",
  "model": "large-v3-turbo",
  "language": "ru",
  "compute_type": "float32",
  "batch_size": 1
}
```

Для другой модели WhisperX измените `model`. Дополнительно можно задать `python`
как путь к Python готового окружения и `library_path` как каталог библиотек FFmpeg.
Без них используются `~/.venvs/whisperx/bin/python` и
`/opt/homebrew/opt/ffmpeg@7/lib`. Выполнение — CPU. Для временного режима одного
спикера добавьте `"diarization_model": "none"`: этап диаризации пропускается.
Без этого параметра диаризация включена. Смена модели не требует пересборки приложения.
Нужные модели ASR, alignment и, при включении, diarization должны быть заранее скачаны;
команда работает с локальным cache и не устанавливает зависимости.
Параметры закрепляются при постановке записи в очередь. Смена модели применяется
к новым задачам; повтор уже начатой задачи использует прежние параметры.

### Parakeet-MLX на Apple Silicon

Для Parakeet FP32 на GPU используйте тот же `stt-engine.json`:

```json
{
  "engine": "parakeet-mlx",
  "model": "mlx-community/parakeet-tdt-0.6b-v3",
  "language": "auto",
  "device": "gpu",
  "compute_type": "float32",
  "chunk_duration": 60,
  "overlap_duration": 5,
  "diarization_model": "none"
}
```

По умолчанию запускается `~/parakeet_env/bin/python`, активация venv не нужна.
ASR работает на GPU. `diarization_model: "none"` пропускает диаризацию и назначает
всему тексту одного условного говорящего (`SPEAKER_00`). Чтобы вернуть определение
говорящих, замените только это значение на `pyannote/speaker-diarization-community-1`:
после ASR модель освобождается и pyannote выполняет диаризацию на CPU.
Код и зависимости диаризации сохраняются. Это обработка готового WAV. Язык Parakeet определяет автоматически,
но его API не выдаёт код языка, поэтому в разговоре он не выдумывается.

Проверенные зависимости перечислены в
[`requirements-parakeet-mlx-macos.txt`](../scripts/dev-harness/requirements-parakeet-mlx-macos.txt).
Нужны Apple Silicon, Python 3.14.6 и FFmpeg; для TorchCodec проверен каталог
`/opt/homebrew/opt/ffmpeg@7/lib`. Python и library path можно переопределить
полями `python` и `library_path`. FP32 не требует локального исправления bf16.
Cache должен содержать config/weights Parakeet, а при включённой диаризации —
Community-1 и его вложенные модели. Доступ к gated-весам pyannote настраивается при подготовке cache.
Штатный обработчик не скачивает веса и не устанавливает пакеты.

При запуске автообработчика проверяются импорты, наличие основных cache-файлов
и фактическое вычисление на GPU. Полный проход WAV дополнительно проверяет
загрузку весов и диаризацию. Проверка выполнена в новом ML-процессе текущего Mac;
установка на чистую macOS отдельно не проверялась.

Если обновлён код адаптера, перезапустите только idle-обработчик через
`auto-transcribe-off` / `auto-transcribe-on`. Бэкенд и приложение пересобирать
не требуется. При смене только настроек новые задачи подхватят их автоматически;
задачи, уже попавшие в очередь, сохраняют прежний профиль.

### Контракт адаптера

Адаптеры `run_whisperx` и `run_parakeet` находятся в
`scripts/dev-harness/dev_harness/local_stt.py`. Другой адаптер должен вернуть:

```json
{
  "language": "ru",
  "segments": [
    {"text": "Проверка.", "speaker": "SPEAKER_00", "start": 0.12, "end": 1.8}
  ]
}
```

`words` внутри сегмента необязательны; при наличии разных говорящих они нужны
для разделения реплик. Время — секунды от начала WAV. Метки говорящих
не являются идентификацией человека. Для другого движка требуются адаптер и
регистрация в настройках, без изменения Omi API или мобильного формата.

## Повтор и ограничения

Исходный JSON и параметры сохраняются приватно в
`.local/dev-harness/ngrok/services/local-transcripts/`, вне Git. Повтор команды
для того же WAV и настроек использует сохранённый JSON; разговор создаётся
только если его ещё нет. Изменённые настройки создают отдельный результат.
После потери состояния эмулятора повтор команды восстанавливает разговор из JSON.
Уже завершённые задачи автоматического обработчика в этом случае нужно
восстановить ручной командой.

Очередь хранится рядом с результатами в приватном `watch-queue.json`.
После прерывания незавершённая задача повторяется; сохранённый JSON используется
повторно, готовый разговор не дублируется. Ошибки повторяются до трёх попыток
с паузами 60 и 120 секунд. После этого задача получает статус `failed`;
исправьте причину и повторите ручную команду для нужного WAV.

Ошибка распознавания, пустой результат или неверные таймкоды не создают готовый
разговор. WAV не удаляется. Одновременно выполняется одна обработка; приём нового
аудио бэкендом продолжается. Проверены WhisperX 3.8.6/CPU/float32/batch 1 и
Parakeet-MLX 0.5.2/GPU/FP32; диаризация — pyannote.audio 4.0.7.

Автономная запись с последующей загрузкой, потоковый текст,
воспроизведение WAV из разговора и LLM-сводка сюда не входят.
Пересборка приложения для этой интеграции не требуется.
